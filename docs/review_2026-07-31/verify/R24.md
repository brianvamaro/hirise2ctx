## Verdict reasoning

**Every number reproduces exactly, and the mechanism is in the code as described.** This is
category (f): real and correctly stated. What I tried in order to kill it:

1. **"The NaNs are legitimate undefined folds."** Killed. `per_fold_metrics` tags a fold
   `is_specificity_only` only when `np.unique(y_true).size < 2` (`evaluate.py:334`), and all 20 folds
   have 41–92 distinct truth values. The NaN comes solely from the second clause of
   `spearman_safe` — `np.unique(y_pred).size < 2` (`evaluate.py:65`). I confirmed this directly from
   `predictions.parquet`: 15 folds have `y_pred` collapsed to a single value (e.g. fold 11 predicts
   0.041308 for all 91 tiles). A constant prediction carries **zero** ranking information, so ρ = 0
   is its unbiased value; excluding it is one-sided-optimistic by construction.
2. **"Some other aggregation rescues the ladder."** Killed under all three I tried. Mean with
   degenerates at 0 = **0.101** (below S=8's 0.118); tile-weighted = **0.097**; pooled
   within-fold-rank ρ = **0.169** — still *below* S=64's 0.262. The claim at
   `docs/modeling_results.md:1079-1080` ("climbs strongly and **monotonically**… Spearman
   0.26 → 0.41 from S64 → S128") does not survive any of them. Note S=8→S=64 (0.118 → 0.263, 20/20
   folds each) is untouched and remains a clean monotone rise — only the S=128 rung is fabricated.
3. **"It is pinned by a test as intended behaviour (d)."** Partly, and it does not save the finding.
   `test_spearman_safe_returns_nan_for_constant_input` (`tests/test_modeling_evaluate.py:26-28`)
   pins the per-fold NaN, which is fine and documented. But
   `test_aggregate_fold_metrics_separates_specificity_folds` (`:117-131`) places its NaN on the
   specificity fold, which `real = [...]` at `evaluate.py:387` already excludes — so **no test
   exercises a NaN on a real fold**, and nothing pins `spearman_n` against `n_real_folds`.
4. **"Deliberate and documented (c)."** Killed. `DECISIONS.md` has no S=128 effective-n caveat
   (only `:1605-1607`, which *restates* the 0.26 → 0.41 claim as Stage 6a's justification, and
   `:3888`, an unrelated Tier-2 note). The project demonstrably knows the failure mode — it wrote
   exactly this caveat for a different metric at `docs/modeling_results.md:957-959` ("`bc_ge_1` AUC
   there is computed on 26 of 38 images — read it with that in mind") — and did not apply it here.
5. **"The blast radius is wider than claimed, so the register understates it"** — checked and it is
   not, for the optimistic channel. Of 236 committed `metrics.json`, exactly **five** have a
   constant-prediction Spearman drop, and four of them move by ≤ 0.011. Structurally this is
   expected: `spearman_rho` is the **only** per-fold metric whose NaN is model-dependent —
   `presence_auc` NaNs only when a truth class is missing (`:138`), and `pr_auc` /
   `meaningful_auc` / `precision@k` NaN only when `n_meaningful_pos == 0 or n_meaningful_neg == 0`
   (`:365,374`). That also means the Stage-6a arm-vs-arm Δs are safe: their dropped folds are
   truth-determined and therefore identical across arms (`spearman_n = 20` in both arms anyway).
6. **"Something shipped depends on it."** No. The frozen recipe is Fang-ViT embeddings at S=32;
   `config_v2.yaml` still lists `[8,16,32,64]`; the S=128 result was explicitly held as dev-only
   (`modeling_results.md:1085-1088`). ROADMAP marks `PLAN_ModelImprovement` "shipped & historical"
   and PROMOTION_QUEUE Part B "done". The claim also never reaches the external-facing writeups
   (`docs/methods.md`, `docs/index.md` contain no S=128 text).

**Mechanism worth recording (not in the finding).** The degeneracy is a hyperparameter/scale
collision, not bad luck: `snapshot.json` pins `min_data_in_leaf = 64`, `num_leaves = 63`,
`early_stopping_rounds = 40`, while the `within_image_4fold` scheme trains on the other 3 quadrants
of the *same* image — ≈ 180–220 rows per fold at S=128 (1228 tiles / 5 images). A fixed
`min_data_in_leaf = 64` against ~200 rows leaves the magnitude booster unable to split, so it emits
its base value. Tiles shrink 16× per scale doubling-squared, so this failure mode is *guaranteed* to
appear at the top of any scale ladder run with fixed leaf constraints. Same family as R32's
degenerate boosters.

**Why high, not blocker:** it invalidates a documented conclusion (§10.2 "640 m tiles are the best
operating scale tested") and a stated research-leg justification, but no shipped deliverable number,
no verdict on the live path, and the leg it helped open (Stage 6a) reached its conclusion on its own
directly-measured, fold-matched evidence. **Why not lower:** the number is wrong by 4×, it is still
asserted as fact in `docs/modeling_results.md`, `PROMOTION_QUEUE.md` (a docket ROADMAP:42 calls
"forward-looking") and `PLAN_ModelImprovement.md`, and §10.2 actively invites future compute
("promotion is just a config flip + re-run").

## Corrected claim

As stated. Three refinements that change what to do about it:

1. **The artifact is not corrupt — the write-up is.** `spearman_n = 5` is present in
   `metrics.json` *and* printed in the same row of
   `models/_sweep_within_image/20260529T184348Z/aggregate.parquet`, directly beside
   `n_real_folds = 20` and `spearman_rho_mean = 0.405615` (rows 0–4 read
   `spearman_n = 20, 20, 20, 20, **5**`). The count was one column away from the number and was
   still written up as "20 folds".
2. **Blast radius, tightened:** exactly 1 of 236 committed cells is materially distorted
   (Δ +0.304); 4 more by ≤ 0.011; 0 shipped numbers; the Stage-6a/6b Δs and the full-v2 38-fold
   comparisons (`DECISIONS.md:2507-2512`) are over matched fold sets and survive.
3. **A second, broader instance the finding does not name:** `presence_auc_mean` is emitted with no
   `_n` at all and is a mean over **24–26 of 38** folds in the full-v2 S=64 regression cells (and
   74 of 152 in the 152-fold within-image cell). It is truth-driven, so it is not *optimistic*, and
   CLAUDE.md bans reporting presence AUC anyway — so this damages nothing today, but it is the same
   silent-population defect and any future reader of those cells is misled.

## Fix assessment

The register's fix is **half right and mis-prioritised**.

- ❌ *"emit `f"{key}_n"` for every aggregated key"* — correct hygiene (and it is the right fix for
  the `presence_auc_n` gap in (3) above), but it **would not have prevented this error**: the count
  that mattered was already emitted, twice. Do it, but do not treat it as the guard.
- ✅ *"count constant-prediction folds separately (`n_degenerate_pred`) rather than sharing the NaN
  channel"* — this is the fix with teeth. Strengthen it: in `aggregate_fold_metrics`, distinguish
  `y_pred`-constant folds from truth-undefined folds and **score the former at ρ = 0 in
  `spearman_rho_mean`** (the unbiased value for a no-information ranker) while reporting
  `n_degenerate_pred` alongside. That makes the default number honest instead of relying on a reader
  to cross-check `spearman_n`.
- ➕ Missing from the register: a **test**. `tests/test_modeling_evaluate.py` must gain a case where
  a *real* (non-specificity) fold carries a NaN, asserting both the reduced `spearman_n` and the new
  `n_degenerate_pred`. The existing aggregation test NaNs only the specificity fold, which is why
  this was invisible for two months.
- ➕ Missing from the register: a **run-time guard in the sweep**, since the root cause is
  `min_data_in_leaf = 64` colliding with ~200-row folds. `sweep_within_image.py` should refuse to
  report a cell (or flag it in `aggregate.parquet`) when > 25 % of folds emit a constant prediction.
- ✅ Doc retraction — correct and the cheapest high-value action. Exact edits:
  `docs/modeling_results.md:1068` (drop "20 folds" → "20 quadrant folds; ρ defined on 5 of 20 at
  S=128"), `:1077` (annotate the 0.406 cell as n=5/20, or replace with 0.101), `:1079-1080`
  (retract "monotonically" / "0.26 → 0.41"), `:1085-1088` (kill the "config flip + re-run"
  invitation), `:1319-1321`; `PROMOTION_QUEUE.md:191-192`, `:653-654`, `:708-710`, `:727`, `:745`,
  `:876`; `PLAN_ModelImprovement.md:145-146`; `DECISIONS.md:1605-1607`. Since Stage 6a's *direct*
  evidence is unaffected, the retraction removes a justification but does not overturn Stage 6a's
  verdict — say so explicitly in the DECISIONS entry so a future session does not reopen the leg.
