## Verdict reasoning

The defect is real, and I could not kill it on any of the four escape routes.

**(a) factually wrong?** No. `src/ctx_retrieve.py:433` calls `src.read(window=window)`, which with
`boundless=False` internally crops the window to the dataset; `:434` calls
`src.window_transform(window)` on the **un-cropped** object; `:445-446` then sizes the output profile
from `data.shape`. So the written raster has the *cropped* extent and the *un-cropped* origin. The
synthetic run above confirms this end-to-end on the installed rasterio 1.5.0 / GDAL 3.11.4: for a
west overhang the output holds tile columns 0…99 while the transform says the first column is 1 500 m
west of the tile edge. The finding's directional claim is also exactly right — west/north overhang
misregisters, east/south only truncates.

**(b) unreachable / guarded upstream?** No. The Murray tile is taken verbatim from the manifest's
`CTX_TileName` (`src/ctx_tiles.py:49-51`) with no check that the Stage-1 polygon footprint lies inside
it. `compute_window_bounds` / `_snap_bounds_to_pixel_grid` snap *outward* and are tile-origin-relative,
so they happily produce negative offsets. Neither `extract_ctx_window` nor `stage2_one_image` compares
`actual_bounds_target_crs` to `requested_bounds_target_crs` — `stage2_one_image:590-593` reads the bad
values back and files them as provenance. `scripts/run_stage2.py` and `scripts/sweep_stage2.py` only
*print* shape/coverage. The Stage-4 protection is a hardcoded ObsId set
(`run_stage4.py:38`), so it protects only the one already-known image, not a new one. And the crop
branch demonstrably fires on real inputs: 1 of 49 cached windows.

**(c) deliberate and documented?** Only half. `DECISIONS.md:397-424` does record the incident and does
defer the fix — but with the **wrong mechanism**: "the strip is entirely WEST of x=0 so it's outside
the E000_N40 tile and *reads as zero pixels*". It does not read as zero pixels: the crop reads *in-tile*
columns 0…203. I confirmed this without opening the raster — the cached `.tif` is 406 830 bytes of
deflate for a 705 636-byte uint8 array (ratio 0.58), whereas the identically-shaped, 917-of-705 636-set
HiRISE mask compresses to 2 174 bytes; a zero or constant band cannot exceed ~1 kB. The deferral was
therefore taken against a benign failure mode that does not exist, and it remains open
(`DECISIONS.md:1353-1354`, "Open at this date"). Nothing in `ROADMAP.md` or any `PLAN_*.md` documents
the transform behaviour as intended.

**(d) pinned by a test?** No. `tests/test_ctx_window_geometry.py` never calls `extract_ctx_window` —
it tests only bounds snapping against a synthetic affine. `tests/test_stage2_one_image.py:91-99` *does*
contain a containment assertion strong enough to catch this
(`win_xmax >= poly_xmax + buffer_m - 5.0` would fail on ESP_057469_2215 by 9.6 km), but it is
`@pytest.mark.slow`, hardcoded to the healthy `ESP_069669_2220`, and skipped unless the 1.5 GB tile zip
is present. So the correct behaviour is asserted for one good image and nowhere in production code.

**Not a convention.** `src/colour.py:147-152` and `src/hirise_imagery.py:237-252` both do
`clipped = window.intersection(Window(0, 0, ds.width, ds.height))` and derive the transform from
`clipped` — and `hirise_imagery` even raises a long diagnostic on empty intersection. `extract_ctx_window`
is the one site out of three that does not. Oversight, not design.

**Blast radius — judged independently, and the register is right.** No shipped number is wrong.
48 of 49 unique cached windows have `actual_bounds == requested_bounds` to 0.00 m; the one bad window
is excluded from Stage 4/4b/5 by name. Two things the register did not quantify, both of which
*strengthen* the "latent hazard" framing rather than weaken it:
- the tightest *surviving* margin is **915 m** (ESP_054134_2265) and 8 of 49 windows sit within 10 km
  of a tile edge — a 1-km change in `buffer_m` or a few more detections would have tripped a second one;
- with an 11.4 km median window against a 237.1 km tile, a uniformly-placed new manifest row has a
  **≈9 %** chance of overhanging on some axis, and a partial straddle keeps a perfectly ordinary
  `hirise_coverage_fraction` (the cohort sits at 0.43–0.67; a 50/50 west straddle would land in that
  band) while every tile in the image is misregistered by half a window width, i.e. ~5 km.
- I extended the map-path check the register began: **all** `read_tile_window` call sites clamp their
  offsets — `window_offsets` in `map_region.py:96-115` (also used by `striping_a1_map.py:122`) caps at
  the tile-aligned `extent - win`; `_evidence_gapfill_map.py:62-63` uses
  `max(0, min(c - WIN//2, tw - WIN))`; `map_pilot.py:74-81` clamps via `clamp(v, hi) = max(0, min(v, hi - win))`;
  `striping_a1_infer_crop.py:40` uses in-range literals. So the same `window_transform`-on-unclipped
  pattern at `src/mapping.py:64` is unreachable today. The register's blast radius is correct: Stage 2
  only.

**Severity.** Kept at **high**, not raised to blocker (no shipped number or verdict is invalidated) and
not lowered to medium: this is silent data corruption on the path CLAUDE.md invariant 7 explicitly
promises ("adding a manifest row + its detection folder must flow end-to-end with no code changes"),
it defeats every existing diagnostic including the coverage fraction, and it has already fired once in
49. The liveness tag `live-shipped` is accurate for the code — it is the only Stage-2 window path for
both configs and produced all 49 shipped windows — but I would add that it is currently **dormant**:
the active work (`PLAN_RegionalMap`, thermal legs) runs the map path, not Stage 2, so the defect cannot
bite until someone adds a manifest row. That makes the fix cheap to schedule, not urgent to hotfix.

## Corrected claim

As stated, with three small refinements:
1. the crop reads tile columns **0…203** (204 columns), not "0…204";
2. the misregistration applies to **west and north** overhang (I confirmed north independently:
   +1 000 m / +200 px on a synthetic 1 000 m north overhang); east/south overhang is *correctly*
   georeferenced but silently truncated, so its failure mode is *missing* tiles, not wrong ones;
3. the "1 of 49" reachability figure is over 49 **unique** windows — the repo actually holds 88
   sidecars because `cache_v2_dev/` duplicates `cache_v2/`.

## Fix assessment

The register's **primary** fix is correct and I verified the API: `Window.crop(height, width)` exists
in rasterio 1.5.0 and returns exactly what `read()` uses internally, so

```python
clipped = window.crop(src.height, src.width)      # or window.intersection(Window(0, 0, src.width, src.height))
if clipped != window:
    raise RuntimeError(f"{out_path.name}: requested window {window} overhangs tile "
                       f"{src.width}x{src.height} -> {clipped}; footprint spans >1 Murray tile")
data = src.read(window=clipped)
new_transform = src.window_transform(clipped)
```

is a faithful and minimal patch. Two corrections to the register's wording:

- **The stated alternative — "or re-read `actual_bounds` from the returned array shape" — does not
  work** for the west/north case. The array shape gives you width/height; the origin is still the
  falsified one, so recomputing bounds from `shape × (wrong transform)` reproduces the wrong bounds
  exactly (which is precisely what `stage2_one_image:590-593` already does). Only deriving the
  transform from the *clipped* window fixes the georeferencing.
- The proposed `assert actual_bounds ≈ requested_bounds` **is** a valid *detector* (a west overhang
  shifts `xmax`, a north overhang shifts `ymin`, so the assertion fires either way), and is worth
  keeping in `stage2_one_image` as defence in depth — but the raise belongs inside
  `extract_ctx_window`, where the clip is observable, so the failure names the real cause
  (multi-tile footprint) rather than a bounds mismatch.

Additional items the register does not mention but that I would bundle:
- **Correct `DECISIONS.md:410-412`** ("reads as zero pixels" → "reads in-tile pixels stamped with the
  overhang's coordinates"), and update the still-open item at `DECISIONS.md:1353-1354`. Left
  uncorrected, the next reader re-derives the benign conclusion.
- **Add a fast unit test** exercising `extract_ctx_window` against a synthetic tiny GeoTIFF for the
  W/N/E/S overhang cases (my `scratchpad/synth_test.py` is directly reusable and runs in <1 s with no
  network) — the existing containment assertion is `slow`-marked and pinned to one healthy ObsId, so
  the regression surface is currently untested.
- Optional and cheap: DECISIONS' own **option (c)** (reproject polygons under a different central
  meridian) resolves ESP_057469_2215 specifically, but does *not* remove the class hazard — the
  clip-and-raise does.
